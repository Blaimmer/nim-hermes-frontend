# NIM PC v2 — Plan de Reconstrucción usando Hermes Desktop como Referencia

> **Para Hermes:** usar subagent-driven-development para implementar tarea por tarea.

**Goal:** Reconstruir la app NIM PC (Tauri) tomando el frontend React + protocolo del cliente
de Hermes Desktop (MIT) y las tools agenticas del harness (127 tools Python, MIT), para que
la app local de Nimrod tenga streaming real, file browser, git review, terminal, y ejecute
tools locales sin depender del bridge roto.

**Architecture:** La app NIM PC es un cliente Tauri (Rust) + frontend React/Vite que hoy se
conecta al VPS vía WSS bridge (:9876). El plan la migra a hablar el MISMO protocolo JSON-RPC
que Hermes Desktop usa contra `hermes serve` (:9119), y portar las tools del harness que
faltan en el bridge. Tres capas: (1) protocolo cliente, (2) UI React, (3) tools locales.

**Tech Stack:**
- Tauri 2.x (Rust) — shell, filesystem, process (ya en package.json: @tauri-apps/api ^2.11, plugin-shell ^2.3)
- React 19 + Vite 6 + Tailwind 4 (ya instalados)
- Referencia UI: ~/.hermes/hermes-agent/apps/desktop/src/ (Electron, MIT)
- Referencia protocolo: ~/.hermes/hermes-agent/apps/desktop/src/api/*.ts
- Referencia tools: ~/.hermes/hermes-agent/tools/*.py (127 tools)
- Repo: /home/clawd/nim-hermes-frontend (git, main, remote Blaimmer/nim-hermes-frontend)

## Riesgos / Decisiones abiertas

1. **Dual-mode (serve vs bridge):** decidir si la app habla :9119 directo (como Desktop)
   o sigue vía bridge :9876. Recomendación: mantener bridge para tools PC (nim_*),
   añadir :9119 solo para UI/sesiones. → Decisión de Nimrod.
2. **Computer use en Windows:** el Cua Driver 0.20 del harness usa contracts; portar
   requiere probar en Windows real. Riesgo medio.
3. **Streaming:** el bridge legacy no soporta streaming — Fase 1.4 lo resuelve con modo serve.
4. **Seguridad:** al exponer :9119, mantener auth basic + recomendación Tailscale (pendiente).
